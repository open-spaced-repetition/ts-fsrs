## 1. FSRS-6 を維持して v6 API に移行する

### スケジュール方針を定義する

`defineScheduler({ model, chrono })` は再利用可能な定義を作成します。`.use(...)` は middleware を組み合わせた新しい定義を返し、`.create({ config })` は設定を検証して独立したスケジューラーを作成します。定義はアプリケーション全体で保持し、ユーザーやデッキの設定に応じてインスタンスを作成してください。

定義だけでは **v5 のすべてのスケジュール方針は含まれません**。以下は現在の標準プリセットと同じ順序で middleware を組み合わせます。目標保持率、ファジング、統計、予定日数、学習ステップ、最大間隔、単調間隔の順です。実際の設定と FSRS-6 の重みを引き継いでください。`dateChrono` の `fractionalDays: false` は UTC 暦日の差を使います。API だけを移行する段階では、影響を検証せずに時間の計算方針まで変えないでください。

ローカルの `StoredV5Card` 型はアプリケーションの保存形式を表し、legacy ライブラリからの import ではありません。データベースの既存の固定 ID を `cardId` に渡し、アプリケーション固有のフィールドは別途保持してください。合成されたカード schema が変換後の日付とフィールドを検証します。その他のアプリケーション固有のフィールドも、保存データを読み込む境界で検証してください。

### カード、ログ、操作

| v5 の保存フィールド | v6 のフィールドまたは処理 |
| --- | --- |
| `due` | カードの `dueAt`。`Date` にデシリアライズします。 |
| `elapsed_days` / ログの `last_elapsed_days` | 削除されました。選択した chrono とタイムスタンプから経過日数を計算し、FSRS-7 のリプレイに古い丸め済みの値を使わないでください。 |
| `last_review` | `lastReviewAt`。未設定と null は `null` に統一します。 |
| `scheduled_days` | middleware が提供する `scheduledDays`。 |
| `learning_steps` | middleware が提供する `learningStep`。 |
| `stability`、`difficulty`、`state`、`reps`、`lapses` | API 移行時に維持します。統計には middleware が必要です。 |
| アプリケーションのレコード ID | `cardId`。カードとログで同じ ID を使います。 |
| 対応するフィールドなし | `scheduleStatus`：New → `new`、Learning/Relearning → `learning`、Review → `review`。 |
| 復習ログの `review` | `reviewTime`。カードの期日ではなく実際の復習時刻です。 |
| 結果 `{ card, log }` | `{ card, revlog }`。 |

サンプルのようにスケジューラーから型を推論してください。カードとログのフィールドはモデル、chrono、middleware によって変わります。独自の v5 strategy は対応する [middleware](./middleware) の hook に書き換える必要があります。名前の変更や旧スケジューラーの継承だけでは移行できません。

| v5 の操作（比較用） | v6 の操作 |
| --- | --- |
| `createEmptyCard(now)` | `scheduler.newCard({ now, cardId })` |
| `f.next(card, now, grade)` | `scheduler.review({ card, now, grade })` |
| `f.repeat(card, now)` | `scheduler.preview({ card, now })` は `Symbol.iterator` で iterator を提供する iterable を返し、`for...of` で走査できます。各候補には `{ grade, card, revlog }` が含まれます。評点をキーにしたオブジェクトへのアクセスではなく、`candidate.grade` で選択します。 |
| `f.rollback(card, log)` | 返された v6 ログを使って `scheduler.rollback({ card, revlog })`。 |
| `f.forget(card, now, reset_count)` | `scheduler.forget({ card, now })`。`{ card, log }` ではなくカードを返します。手動操作はアプリケーションで記録します。 |
| `f.get_retrievability(card, now, false)` | `lastReviewAt` のある学習済みカードでは `scheduler.model.forgettingCurve(card, scheduler.chrono.difference(card.lastReviewAt, now))`。戻り値は数値です。新規カードは別途処理し、パーセント表示はアプリケーションで整形します。 |

`review()` は新しいデータを返します。`result.card` と `result.revlog` の両方を保存してください。新しいログは `dueAt`、`lastReviewAt` など、取り消しに必要な復習前のフィールドを保持します。旧ログの `due` を改名するだけで v6 の取り消しに使わないでください。旧ログには復習前のスナップショットが不足している場合があります。元の履歴は維持し、モデルのリプレイ用には評点と実際の復習時刻だけを変換します。バージョンをまたぐ取り消しには、アプリケーションの独立したスナップショットか取り消し境界が必要です。

モデルと設定が同じでも、すべての学習ステップやファジングで v5 と同一の間隔になる保証はありません。書き込みを切り替える前に New、Learning、Review、Relearning の代表カードを検証してください。[DefaultScheduler](./scheduler/default-scheduler) も利用できますが、デフォルトモデルは FSRS-7 です。この段階で使う場合は FSRS-6 を明示してください。

### ログの 3 つの時刻は単なる改名ではない

`dateChrono` のフィールド名は **`reviewTime` であり、`reviewAt` ではありません**。前回の復習が 1 月 1 日、元の期日が 1 月 3 日、実際の復習が 1 月 4 日という延滞の例を考えます。

| 意味 | v5 の通常の復習ログ | v6 の `revlog` |
| --- | --- | --- |
| 前回の復習時刻：1 月 1 日 | `due`（旧実装は `card.last_review \|\| card.due` を記録） | `lastReviewAt` |
| 元の期日：1 月 3 日 | この学習済みカードでは独立した記録なし | `dueAt` |
| 今回の実際の復習時刻：1 月 4 日 | `review` | `reviewTime` |

`lastReviewAt` は**今回の復習より前の、前回の復習時刻**です。入力と出力で型が異なります。

- 入力の `DateRevlogInputFields` では `lastReviewAt?: Date | null` と省略可能です。省略または `undefined` の場合、schema は `null` に正規化します。`dueAt` と `reviewTime` は有効な `Date` が必須です。
- 出力の `DateRevlogFields` には `lastReviewAt: Date | null` が必ず存在します。通常の学習済みカードのログには復習前の `card.lastReviewAt` を記録し、前回の復習がない新規カードの初回ログでは `null` になります。
- `null` から欠落した前回復習時刻を復元することはできません。旧ログにその情報がなければ、schema の検証に通っても正確な取り消しは保証されません。`dueAt` や `reviewTime` で代用しないでください。

復習が返すカードの `lastReviewAt` は 1 月 4 日になり、`dueAt` は新たな期日になります。一方、ログは**復習前**の時刻を保持します。そのカードと v6 ログで取り消すと、`dueAt` は 1 月 3 日、`lastReviewAt` は 1 月 1 日に戻ります。前倒しや延滞でも同様です。経過日数の計算に使う時刻と、取り消しのために保存する期日を分離したのが chrono リファクタリングの理由です。上のサンプルは 3 フィールドを出力します。

一律に `oldLog.due → revlog.dueAt` と変換してはいけません。通常の v5 学習済みカードの `due` は前回の復習時刻です。`last_review` のない初回復習では元の期日になり、Manual／忘却のログには別の意味があります。リセット済みの v5 New カードにも古い `last_review` が残る場合があるため、カード変換サンプルでは `State.New` の `lastReviewAt` を `null` にします。

モデルの記憶だけを再構築する場合は、`rating` と `review → reviewTime` の変換で十分です。バージョンをまたいで正確に取り消すには、両方の時刻と middleware フィールドを含む元の復習前カードのスナップショットが必要です。それがなければ取り消し境界を設けてください。前倒し復習、学習ステップ、ファジング、手動調整があると、`review` や再計算した間隔から未記録の期日を復元することはできません。

## 2. FSRS-6 から FSRS-7 に移行する

### 重みと状態はモデル固有

FSRS-6 は 21 個、FSRS-7 は独立した **34 個の重み**を使用します。`FSRS7_DEFAULT_WEIGHTS` を使うか、[FSRS-7 の重みを再学習](./optimizer)してください。FSRS-6 のベクトルに値を追加したり、その学習済み重みを流用したりしないでください。`migrateFSRS7Parameters` は空の入力にデフォルト値を提供しますが、旧モデルのパラメーター配置を変換するものではありません。

FSRS-7 の記憶状態は `stability`、`stabilityFast`、`difficulty` です。3 つとも履歴から再構築してください。**再構築した結果は現在の card の記憶状態（memoryState）だけに適用します。過去の revlog は読み取り専用の入力として扱い、記録済みの記憶状態を含め、データの変更・上書き・後付けをしてはいけません。**

**学習済みカードに `stabilityFast = 0.8 * stability` を設定してはいけません**。FSRS-6 の安定性と難易度を維持したまま高速成分だけを追加する方法も使えません。モデル初期化時の係数は、更新を重ねた記憶状態の移行式ではありません。

`fractionalDays: true` にして、10 分間隔の復習などを小数日数のまま保持してください。FSRS-7 の高速トレースはモデル固有です。学習ステップの middleware を使用した場合、`enableShortTerm: false` が無効にするのは明示的な学習ステップだけで、高速トレースは無効になりません。FSRS-7 モデルには FSRS-6 の `numRelearningSteps` に対応する設定はありません。

### FSRS-7 のデフォルトステップと学習状態

`DefaultScheduler` は FSRS-7 で `learningSteps: []` と `relearningSteps: []` をデフォルトとし、モデルが間隔を決定します。FSRS-3～6 は学習ステップ `['1m', '10m']` と再学習ステップ `['10m']` を維持します。明示した設定はデフォルト値で上書きされません。`enableShortTerm` は引き続き `true` がデフォルトで、明示的なステップを制御します。FSRS-7 の高速トレースや間隔による状態分類は無効にしません。

`schedulerLearningStepsMiddleware` が登録されている場合、ステップが無効・空・完了済みでも、**最終スケジュール間隔**で状態が決まります。

| 復習前の状態 | 最終間隔が 1 日未満 | 最終間隔が 1 日以上 |
| --- | --- | --- |
| New / Learning | Learning、`scheduleStatus: learning` | Review、`scheduleStatus: review` |
| Review / Relearning | Relearning、`scheduleStatus: learning` | Review、`scheduleStatus: review` |

ステップを無効にすれば Learning がなくなる、Again だけが Relearning を生む、Easy は必ず Review になる、という前提は使えません。Easy は明示的なステップをスキップし、Good は適用可能な次のステップがある場合のみ進みます。明示的なステップが間隔を提供しない場合、`learningStep` は `0` に戻りますが、Learning/Relearning のままの場合があります。これはステップ番号であり、復習回数ではありません。

状態遷移は middleware の責務で、`FSRS7Model` の責務ではありません。モデルと chrono だけのスケジューラーは、間隔が 1 日未満でも Review を返します。旧動作を前提としたキュー、状態フィルター、統計の処理も更新してください。

[「記憶をリプレイし、スケジュールを維持する」の完全な移行サンプル](#記憶をリプレイしスケジュールを維持する)は、設定省略で FSRS-7 の空ステップのデフォルトを採用せず、**既存の学習ステップを明示して維持**します。製品としてモデル主導のステップを選ぶ場合は `learningSteps: []` と `relearningSteps: []` を明示してください。学習ステップ middleware を削除するという意味ではありません。方針の変更はカードフィールドの移行と分けて検証してください。

### 想起確率の呼び出しを移行する

`scheduler.model.forgettingCurve(state, elapsedDays)` で数値の想起確率を取得し、`scheduler.model.algorithm.curve(elapsedDays, state)` で両成分を確認できます。どちらも `stability`、`stabilityFast`、`difficulty` を含む FSRS-7 の完全な状態が必要で、FSRS-6 の安定性 1 値だけは渡せません。

または `ts-fsrs/models/fsrs-7` から独立した `curve` を import し、`curve(weights, elapsedDays, state)` を呼び出せます。アルゴリズムのインスタンスは不要です。有効な 34 個の FSRS-7 の重みを渡してください。**この関数は重みを検証しません**。保存データやユーザー入力は事前に schema・パラメーターチェックで検証し、`curve` の呼び出しを妥当性チェックに使わないでください。再構築した記憶状態と同じ FSRS-7 の重みを使い、`elapsedDays` の小数部分を保持してください。

曲線の戻り値は `retrievability`、`derivative`、`fast`、`slow`、`fastWeight`、`slowWeight`、`total` を含みます。`total = fastWeight + slowWeight` は混合係数の和であり、全体の想起確率ではありません。旧確率呼び出しの代わりには `retrievability` を使い、パーセント表示はアプリケーションで整形してください。アルゴリズムインスタンスの曲線結果にも `total` が含まれます。これらの API は確率と成分の計算用であり、カード移行、ログ生成、期日の設定は行いません。

### 記憶をリプレイし、スケジュールを維持する

以下は単独で実行できます。v6 形式に変換済みの FSRS-6 カードを受け取り、保存ログの `review` を `reviewTime` に変換して `Reschedule.replay()` を呼びます。旧モデルの `initialState` は渡しません。**移行時は記憶状態だけを再構築し、既存カードの次回復習日時（`dueAt`）は変更しません**。そのカードを次に復習した時点で、FSRS-7 が新しい次回復習日時を計算します。ID、最終復習時刻、学習進捗、統計も維持されます。

| 作成時または最新の記憶リセット以降の完全な履歴がある学習済みカード | FSRS-7 の重みでリプレイし、スケジュールを維持して再構築した状態を保存します。 |

| 不正な日付・評点、または最後の復習が `lastReviewAt` と一致しない | そのカードの移行を止め、記録を確認します。 |

`replay()` は有効な復習を時刻順に並べ、`Rating.Manual` を除外します。ただし手動の忘却・リセットイベントは解釈しません。アプリケーションが**最新の記憶リセット以降**の完全な履歴を選び、それ以前の復習を除外する必要があります。期日を手動調整しただけなら記憶リセットではありません。同時刻の復習は記録順を維持してください。`dateChrono` ではデシリアライズ後の時刻は有効な `Date` である必要があります。最初の復習は未初期化の記憶状態から、経過日数ゼロで開始します。

サンプルの履歴完全性フラグはアプリケーションで判断します。最後の時刻が一致していても、それ以前の復習が欠落していない証明にはなりません。移行できないカードは保存されたモデルバージョンに応じて FSRS-6 に振り分け、FSRS-7 に渡さないでください。

### 意図的に期日も再計算する場合

`new Reschedule(scheduler).reschedule({ history, initialCard })` はスケジュール方針全体を通してリプレイし、`{ card, results }` を返します。期日、学習進捗、統計が変わる場合があります。`initialCard` には、既存の `cardId` と最初の復習時刻を指定した **FSRS-7 の新規カード**を使ってください。学習済みカードに完全な履歴を重ねてリプレイしてはいけません。生成されるログは再計算結果であり、元の履歴の置き換えではありません。このガイドでは `replay()` を標準とし、移行時に既存カードの次回復習日時を変更しません。

## 保存と検証

1. カード、元のログ、設定をバックアップします。モデルバージョンと実際にリプレイに使った重みを、カードまたは確実に関連付けられた設定に保存します。
2. `stabilityFast` と v6 フィールドを保存できるようにし、再構築した記憶、モデルバージョン、対応する重み・設定の参照を一緒に更新します。FSRS-6 の状態と FSRS-7 の重みを混在させず、アプリケーションの ID とメタデータを維持します。
3. 元のログを保持し、取り消しの境界を設けます。旧モデルのログを FSRS-7 の `rollback()` に直接渡してはいけません。新しい FSRS-7 ログには `stabilityFast` と復習前のフィールドを保存します。
4. 代表カードで復習、プレビュー、取り消し、同日復習、学習ステップ、設定したファジングを検証します。記憶だけの移行では期日、ID、学習進捗、統計が変わらないことを確認し、失敗を解消してから該当カードのモデルを切り替えます。

モデルの詳細は [FSRS-7](./model/fsrs-7)、API の構成は[スケジューラー定義](./scheduler)、[Chrono](./chrono)、[middleware](./middleware)を参照してください。
