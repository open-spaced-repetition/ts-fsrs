# Reschedule

`ts-fsrs/reschedule` 子路徑匯出在保留具體型別的情況下、針對排程器重播或重新排程複習的輔助工具：

```ts
import { Reschedule } from 'ts-fsrs/reschedule'
```

`Reschedule<Scheduler>` 包住一個排程器實例，並從中推導出該排程器的卡片、記憶狀態、複習與 result 型別。

## 重播

`reschedule.replay({ history })` 只從複習歷史重建模型的記憶狀態，不碰觸任何卡片：

```ts
const replay = reschedule.replay({ history })
// replay.memoryState      — memory after the last review
// replay.memoryStates     — memory after each review
```

每個歷史項目都是一對 `{ rating, reviewTime }`，其 `rating` 型別會依排程器的評分方案推導（FSRS 為 `Rating`，自訂模型為其評分聯合型別）。從既有記憶狀態繼續時，在第一個參數傳入 `initialState`。兩個方法都接受第二個參數 `{ sortHistory: false }`。預設的 `sortHistory: true` 只在 chrono 提供 `compare` 時排序。`numericChrono` 或未提供 `compare` 的自訂 chrono 會保留輸入順序，因此必須自行依時間排列歷史。`replay` 與 `reschedule` 都會使用 `scheduler.ratings.ratingSchema` 驗證每筆評分（無效值會擲出 `SRSSchemaError`），並略過 `scheduler.ratings.isManual(rating)` 為 `true` 的項目，例如 FSRS 的 `Rating.Manual`（`0`）或 `-1` 這類自訂手動評分；評分方案不含手動評分時不會略過任何項目。歷史至少需要一筆非手動複習。

若排程器是聯合型別，歷史紀錄只能使用所有候選排程器都接受的評分。

## 重新排程

`reschedule.reschedule({ history, initialCard })` 透過排程器重播複習，並回傳每次複習產生的卡片與 revlog：

```ts
const result = reschedule.reschedule({ history, initialCard: card })
// result.results  — the card and revlog after each review
// result.card     — the card after the last review
```

`replay` 只靠歷史就重建出穩定性（`2.3065`）；`reschedule` 則透過排程器重新計算卡片與其到期時間。

若模型的 `forward` 回傳的不是狀態陣列，而是打包的 typed array（例如每次複習對應一列、列寬固定的 `Float64Array`），`memoryStates` 即為該緩衝區本身，`memoryState` 則是其最後一列的 `subarray` 視圖，與 `memoryStates` 共用同一緩衝區。打包模型、排程器與 `Reschedule` 須來自同一個套件（例如全部來自 `ts-fsrs`），不支援混用不同的套件。

**相關型別** — `RescheduleReview`、`NonManualReview`、`ReplayResult`、`ReplayResultOf`、`RescheduleResult`，以及推導型別 `CardOf`、`MemoryStateOf`、`MemoryStatesOf`、`TimeOf`、`ScheduleResultOf`。

**另見** — [defineScheduler](./define/define-scheduler)、[DefaultScheduler](./default-scheduler)。

`ts-fsrs` 的 `FSRSMemoryStateSchema` 描述 FSRS-3–6 的 `{ stability, difficulty }`。FSRS-7 使用 `ts-fsrs/models/fsrs-7` 的 `FSRS7MemoryStateSchema`，增加 `stabilityFast`。舊狀態需透過 `Reschedule` 重播歷史重建；遷移權重不會重建快速軌跡。
