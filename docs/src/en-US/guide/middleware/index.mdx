# Middleware overview

Middleware adds scheduling policies and application fields to a scheduler. The model calculates memory states and intervals, and a chrono preset turns those intervals into due times. Middleware sits between them: it can adjust the target retention or interval, manage learning steps, and maintain extra card data that the model never sees. See [Architecture](../architecture) for how these parts fit together.

:::note Middleware boundary
A scheduler composes a model, a chrono, and middleware. Keep the model limited to memory-state updates and interval math, and let the chrono own time values and day arithmetic. Middleware supplies inputs before the core operation runs, adjusts the result afterward, and carries the fields those two parts do not define.
:::

## Define fields and behavior

A `Middleware` definition has a required `name` and optional schemas, defaults, and handlers. `defineMiddleware()` infers the handler types from those schemas. Import it from `ts-fsrs`; the built-in policies are also exported from `ts-fsrs/middlewares`.

| Definition | Purpose |
| --- | --- |
| `schema.config` | Validates configuration passed to `create({ config })`. Middleware shares the scheduler's config object. |
| `schema.card` | Declares and validates fields on input and output cards. |
| `schema.revlog` | Declares and validates fields on review logs, including values needed for rollback. |
| `schema.cardInitInput` | Declares additional input accepted by `newCard()`, such as a card ID. |
| `defaultValue.card` | Supplies fields when creating or forgetting a card. `ctx.operation` distinguishes the two operations. |
| `handlers.review` / `handlers.rollback` | Update `ctx.result` around the next handler in the chain. See [Lifecycle](./lifecycle) for how these run. |

Schemas provide runtime validation as well as TypeScript inference. This example uses Zod, which implements Standard Schema. Install it alongside ts-fsrs to run the example in your application:

`base.use(streakMiddleware)` returns a new scheduler definition; `base` stays unchanged. Keep the return value or chain `.create()` as above. Because middleware composes through `use`, the handlers run in a fixed order around the scheduler core — see [Lifecycle](./lifecycle).
